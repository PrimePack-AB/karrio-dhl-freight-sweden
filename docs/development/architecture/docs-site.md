The `docs/` tree, minus `docs/notes/`, is published as a Starlight site at <https://primepack-ab.github.io/karrio-dhl-freight-sweden/>.
This repository contains no site application code; it holds the markdown and one workflow file, and the site shell, build, and link handling live in the external harness repository [PrimePack-AB/starlight-docs-harness](https://github.com/PrimePack-AB/starlight-docs-harness).

## Build and publishing

The workflow `.github/workflows/docs-pages.yml` runs on pushes to `main` that touch `docs/**` or the workflow itself, and on manual dispatch.
Its build job checks out this repository and invokes the harness as a composite GitHub Action, pinned by commit SHA with the tag in a trailing comment (currently v1.3, commit 6a9f84b).
The action installs bun, builds the site with `docs-dir`, `exclude` (default `notes`), `title`, `base`, `repo-url`, and `repo-ref` passed as environment variables, and uploads the Pages artifact.
The deploy job deploys that artifact with `actions/deploy-pages`, and only that job holds the `pages: write` and `id-token: write` permissions.
The repository's Pages source is set to GitHub Actions.

Consuming a new harness release means editing the SHA pin and its tag comment in the workflow.
Published harness tags are never force-moved; the v1 tag predates the v1.1 fixes, and this repository's landing page needs v1.2 or later.

A failed build leaves the last good deployment serving, and the failure surfaces in the Actions log.
The `github-pages` environment has no required reviewers, because a required review would leave deployments pending silently instead of failing.
Because the paths filter matches `docs/**`, a push that changes only `docs/notes/` also rebuilds and redeploys unchanged content.

Local preview runs the harness dev server against this repository's `docs/`, using the command in the repository's `CLAUDE.md`.

## Content mounting

The harness mounts content in place: no file under `docs/` is moved, renamed, or converted for the site.
This keeps `tests/dhl_freight_sweden/test_doc_links.py`, which reads the tree with `rglob("*.md")` and checks that relative links resolve and that every sandbox evidence file is linked, valid for both GitHub and the site.

Starlight 0.38 has no loader `base` option and no plugin-level collections, so at build time the harness symlinks each rendered subdirectory of `DOCS_DIR` into its own `src/content/docs/`, and each mounted subdirectory becomes an autogenerated sidebar section.
Since v1.2 the harness also mounts a root `docs/index.md` or `docs/index.mdx` as the site landing page, with the same link rewriting as every other page, and falls back to its own generic landing page only when neither exists.
This repository provides `docs/index.md`, a Starlight `template: splash` page with a `hero`.
Its hero action links are not rewritten, so they are written as site routes that include the `/karrio-dhl-freight-sweden` base path, or as absolute URLs, and it carries no hero image, which would have to sit in a mounted subdirectory.
Other files at the top level of `docs/` are not mounted.
Every page carries `title:` frontmatter, the only field Starlight's default schema requires.

## Link classes

Links divide into three classes.
Relative markdown links between mounted pages are rewritten to site routes under the base path by the harness's `rehype-repo-links` plugin, since Astro does not rewrite relative links itself.
Heading anchors survive unchanged, because GitHub and Starlight both slugify headings with `github-slugger`.
Links to files outside the rendered tree, such as sandbox fixtures, source files, and excluded notes, are rewritten to GitHub `blob` or `tree` URLs built from `repo-url` and `repo-ref`, so they resolve on the site instead of returning 404.
A link the plugin cannot rewrite is reported as a `[rehype-repo-links]` warning in the build output.

`starlight-links-validator` is not used, because fixture links never map to site routes by design.

## Excluded working notes

`docs/notes/` holds ephemeral working notes, including the sandbox findings, and the working-notes convention keeps them out of published documentation.
The harness excludes the directory by not mounting it, so the notes are readable only in the repository, and links to them from published pages become GitHub URLs.

## Disabled Starlight features

Starlight's `lastUpdated` and `editLink` are off.
Both resolve git history and edit paths against the repository the build runs in, which is the harness checkout rather than this repository, so they would show wrong dates and wrong edit targets.
